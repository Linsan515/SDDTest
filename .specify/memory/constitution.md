# SDDTest Constitution

## Core Principles

### I. 規格驅動（Spec-Driven）

- 任何功能在撰寫程式碼之前，**必須**先有經確認的規格（`spec.md`）、
  實作計畫（`plan.md`）與任務清單（`tasks.md`）。
- 規格**必須**描述「要做什麼、為什麼」，而非「如何實作」；技術選擇屬於計畫階段。
- 規格中所有模糊之處**必須**以 `[NEEDS CLARIFICATION]` 標記，並在進入計畫前釐清
  （透過 `/speckit-clarify`）。
- 實作內容若偏離規格，**必須**先更新規格與計畫，再修改程式碼。

**理由**：本專案為 Spec Kit 實驗環境，目的在驗證規格驅動開發流程；
規格是唯一的事實來源，確保需求、設計與實作可追溯且一致。

### II. 測試先行（Test-First，不可協商）

- 嚴格遵循 TDD：撰寫測試 → 確認測試失敗 → 實作 → 測試通過 → 重構（紅—綠—重構）。
- 每個使用者情境（user story）的驗收條件**必須**對應至少一個自動化測試。
- 在對應測試存在且曾經失敗之前，**不得**合併任何實作程式碼。
- 測試**必須**可在本機以單一指令執行，且結果具決定性（不依賴執行順序或外部狀態）。

**理由**：先寫測試能把規格中的驗收條件轉為可執行的契約，
並防止實作超出或偏離規格。

### III. 簡潔優先（Simplicity / YAGNI）

- 只實作規格目前明確要求的功能；**不得**為假設中的未來需求預先設計。
- 優先選擇標準函式庫與最少的相依套件；每新增一個外部相依**必須**在計畫中說明理由。
- 新增抽象層、設計模式或額外專案／模組時，**必須**在 `plan.md` 的
  「Complexity Tracking」中記錄理由與被否決的較簡單替代方案。
- 重複出現三次以上的邏輯才考慮抽象化。

**理由**：沙盒專案的價值在於快速迭代與易於理解；
不必要的複雜度會掩蓋流程本身的問題。

### IV. 可觀測性（Observability）

- 程式**必須**輸出結構化日誌（例如 JSON 或固定 key=value 格式），
  並包含時間戳記、等級與事件名稱。
- 錯誤**必須**以明確訊息回報，包含失敗原因與相關上下文；**不得**靜默吞掉例外。
- 一般輸出寫入 stdout，錯誤與診斷資訊寫入 stderr。
- 日誌**不得**包含密碼、權杖或其他機密資訊。

**理由**：清楚的日誌與錯誤訊息讓問題可被快速定位，
也讓測試與除錯能驗證系統實際行為是否符合規格。

### V. MVP 優先，避免過度設計（MVP-First, No Over-Design）

- 每個功能**必須**先定義並交付最小可行產品（MVP）：能完成核心使用者情境、
  可被測試與展示的最小範圍。
- 規格**必須**將使用者情境標示優先順序（P1、P2…），並明確界定 MVP 範圍
  （通常為 P1）；MVP 以外的情境列為後續迭代，**不得**混入首次交付。
- MVP 完成並驗證前，**不得**開始實作非 MVP 的情境或功能。
- **禁止**過度設計，包括但不限於：為尚未出現的需求預留擴充點、
  建立只有單一實作的介面／抽象層、加入規格未要求的設定項、快取、外掛機制或通用框架。
- 若計畫或實作超出 MVP 範圍，**必須**在 `plan.md` 的「Complexity Tracking」中
  說明理由，否則視為違反本原則。

**理由**：先交付最小可運作的成果，才能及早取得回饋並驗證方向；
過度設計會增加維護成本、拖慢迭代，且往往為了不會發生的需求付出代價。
本原則與原則 III 相輔相成：III 約束「如何實作」要簡潔，V 約束「實作範圍」要最小。

## 品質與技術約束

- 技術堆疊於各功能的 `plan.md` 中決定，並**必須**符合上述四項原則。
- 程式碼**必須**通過所選語言的標準格式化與靜態檢查工具（linter）。
- 機密資訊（API 金鑰、憑證等）**不得**提交至版本庫；應使用環境變數或本機設定檔，
  並將其列入 `.gitignore`。
- 每個功能**必須**能獨立建置、測試與展示，不依賴尚未完成的其他功能。

## 開發流程與品質關卡

1. **規格**：`/speckit-specify` 產生規格，並**必須**明確界定 MVP 範圍；
   必要時以 `/speckit-clarify` 釐清。
2. **計畫**：`/speckit-plan` 產生計畫，並通過「Constitution Check」關卡
   （包含檢查是否超出 MVP 範圍或有過度設計）；
   任何違反原則之處**必須**記錄並說明理由。
3. **任務**：`/speckit-tasks` 產生任務清單，測試任務**必須**排在對應實作任務之前。
4. **分析**：實作前建議執行 `/speckit-analyze`，確認規格、計畫與任務之間一致。
5. **實作**：`/speckit-implement` 依任務順序執行，遵循紅—綠—重構循環。
6. **合併前檢查**：所有測試通過、格式化與靜態檢查無錯誤、
   規格與實作一致，方可合併至 `main`。

## Governance

- 本憲章優先於所有其他開發慣例與文件；若有衝突，以本憲章為準。
- **修訂程序**：修訂**必須**透過 `/speckit-constitution` 進行，並在提交訊息中說明
  修訂內容、理由及對既有規格／計畫的影響。
- **版本規則**（語意化版本）：
  - MAJOR：移除原則或以不相容方式重新定義原則或治理規則。
  - MINOR：新增原則或章節，或實質擴充既有指引。
  - PATCH：措辭澄清、錯字修正等不影響語意的調整。
- **合規檢查**：每份 `plan.md` 的 Constitution Check 與每次程式碼審查
  **必須**確認符合本憲章；未經記錄理由的違反不得合併。
